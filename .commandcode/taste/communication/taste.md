# Communication & reporting preferences

- Wants concise end-of-task reports structured into explicit sections: routes/pages found, missing or broken items discovered, files modified, what was fixed, API/backend mismatches fixed, functionality that could not be verified without a live environment, exact validation commands used, and each command's final result. Confidence: 0.8
- Wants findings tied to exact identifiers — file paths, component/function names, line numbers, routes/triggers, and Git commit/branch attribution — so each claim can be located and verified precisely. Confidence: 0.8
- Appreciates explicitly flagging what could not be verified end-to-end (e.g. flows needing a real driver, socket pairing, SMS, or payment environment) rather than claiming full success. Confidence: 0.8
- Requests token-efficient execution and minimal output (e.g. appends "use min token" to a task spec); keep tool usage and final summaries concise while still covering the required report items. Confidence: 0.8
- Reports bugs and follow-ups tersely — quotes on-screen error messages verbatim (e.g. "Invalid credentials fix this login problem", or a whole observed sequence like "An account already exists with this email/phone. Please log in instead." then "Invalid credentials") with no symptoms, reproduction steps, or account details, and may paste the entire raw browser console dump including full stack traces and unrelated noise (network 401/409s, DevTools banners), or just a single failing entry copied out of the DevTools Network panel (exact URL + request method + status code + referrer policy) as the entire bug report, for the agent to parse; expects the agent to trace, diagnose, and fix autonomously (e.g. digging through logs/DB when the identifier isn't supplied, or pinning a crash to stale Vite cache from the stack) rather than demanding more context. Confidence: 0.8
- Describes a visual bug in prose and says a screenshot is provided ("I have provided a screenshot of the current ride/history route display", "I have provided two screenshots showing…") but the image fails to attach in many tasks (same failure across many tasks) while in others it does arrive intact (e.g. a database-client screenshot of the raw stored rows, pasted as proof the records exist), in which case it is real evidence that must be read; expects the agent to work from whatever actually arrived — the attached image when present, otherwise the written description plus the code (locating the right component and diagnosing the real defect itself, and stating which screen it inferred) rather than refusing to start — while still flagging that the screenshot never arrived. Confidence: 0.75
- Feature requests arrive in the same terse, typo-laden one-liner style (e.g. "convert remaning dark and light theme in remanig pages also languga converter apply all pages dont change other code") with scope left open (which app, which screens, which languages); expects the agent to audit the codebase first and settle only the genuinely ambiguous scope forks before executing. Confidence: 0.6
- An umbrella "fix everything" request (e.g. "solve all bug and apis fix this confidence 100 make", "make confidenc 100% fix all conections") signals an exhaustive, comprehensive pass over ALL bugs and API/socket connections to completion, not a single scoped patch; the user wants the agent to chase every integration gap, deliver at full (100%) confidence, and verify thoroughly even if it goes beyond a token-efficient pass — the recurring "confidence 100%" wording is the signal that completeness/verification matters more than token economy. Confidence: 0.7
- Follows up on a just-completed task with a very short, often typo-laden additive instruction that relies on the conversation context to say what it means (e.g. "also remove tap to speck option" after the chat-header removal; "alos more option navigation for all pages" right after the Ride History scroll fix) — restating no page, component, or file, and leaving the previous uncommitted work in place. The scope is often explicitly app-wide ("for all pages") rather than the single screen just edited; expects the agent to infer the target and apply the same strict, whole-feature treatment there (or across every page when scoped that way). Confidence: 0.7
- Sometimes describes the desired behavior by pointing to an external reference (e.g. a "reference video" showing the target interaction) and gives a structured spec — labeled sections such as REFERENCE BEHAVIOR plus a list of DO-NOT constraints (keep existing UI/colors/images/cards/spacing/icons/functionality unchanged, no API/logic changes, no unnecessary animation/delay, scope limited to the named page) — expecting the agent to reproduce that behavior faithfully rather than inventing UI of its own. Confidence: 0.55
- Sometimes replaces the usual terse one-liner with an exhaustive, formally-structured "MASTER PROMPT" — numbered requirement sections, explicit MUST / DO-NOT rule lists (including a long list of screens/architecture that must remain untouched), an acceptance-criteria checklist of numbered end-to-end tests, and a mandated numbered final-report template (often closing with a "CODE REVIEW" section: run git status/git diff, review every changed file, revert unrelated edits, do not commit or push) — and expects every listed rule and acceptance criterion to be honored and each one verified. Confidence: 0.8
- The same formal style also appears as a self-labelled "fix-only prompt" for a single tightly-scoped bug: a symptom with concrete evidence (counts/log funnel, exact file paths to inspect), a long DO-NOT list of subsystems and behaviours that must stay untouched (socket dispatch, passenger/driver UI, security/auth, subscription & wallet rules, city/vehicle/distance matching), an explicit expected result, and a mandated post-fix deliverable set — run `node --check` on changed files plus backend tests, then show the exact files changed, the root cause, and the before/after behaviour. Wants every constraint honoured (fix only that bug) and the change proven, not just claimed. Confidence: 0.75
- When issuing a formal fix-only prompt, sometimes writes it as an exhaustive numbered STEP-by-STEP procedure with explicit conditional decision branches — e.g. "if socketCount=0 → STOP, do not touch matching, fix ONLY the driver registration/room/reconnect path; if socketCount=1 but the driver still receives nothing → STOP changing room registration and inspect the event name/listener instead" — and prescribes the exact temporary log lines, message prefixes, and field names the agent must emit, so the diagnosis itself is pre-scripted: the agent is expected to follow the given branch logic (and halt at the stated STOP gates) and print the specified logs rather than improvising its own debugging. Confidence: 0.55
