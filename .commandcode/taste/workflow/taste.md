# Workflow preferences

- When the agent presents several concrete options (e.g. run local backend vs. point at deployed API, or a multi-select fork of which local-only features to wire up) and asks which to take, the user delegates the choice ("fix now, make your want", or simply "contune"/"continue" in place of answering the question) and expects the agent to pick the workable/minimal option and execute immediately — not stall on another confirmation round. Confidence: 0.7
- Audits/inspects the full project structure and flow (frontend routes/pages/navigation/API calls, backend routes/controllers/models, socket and status flows) before making any changes. Confidence: 0.8
- Sometimes runs investigation as a strictly read-only phase: no new implementation and no file modifications at all, ending with a report so the user can decide next steps before any code is written. Confidence: 0.8
- Never blindly kills processes on a port conflict: first identifies the PID's working directory and command line (e.g. `lsof -a -p <pid> -d cwd`, `ps`) to determine whether it belongs to the current project; keeps it if it's the correct current instance and stops it only if it is stale/unrelated/trashed (e.g. a copy running from `~/.Trash`) and safe to stop. Confidence: 0.6
- When a feature seems missing after a merge, uses Git history forensics across all branches and commits (string/pickaxe search, blob comparisons across commits, branch membership, commit attribution) to determine whether it ever existed, which commit/branch added or removed it, and whether the merge changed its trigger or reachability. Confidence: 0.8
- The user handles Git operations themselves: do not commit or push; leave fixes in the working tree for review before the user commits. Confidence: 0.9
- Validates work with real commands (frontend lint/build, backend tests) and fixes actual errors; when a failure is clearly caused only by the local environment (e.g. Windows path issues), documents it instead of making unrelated code changes. Confidence: 0.8
- When running diagnostics, prefers throwaway/scratchpad tooling over leaving temporary scripts or test files in the repo working tree, and cleans up after itself — temporary backend instances are stopped and any live data the check created (e.g. a test ride) is cancelled once observed. Confidence: 0.6
- Verifies backend changes against a throwaway instance (a separate port / its own `PORT` + env, same codebase) while the user's already-running server is left completely untouched, then reports that the change is inert until the user restarts their own process — the agent does not kill, restart, or rebind the port of the user's live dev server. Confidence: 0.6
- For a bug fix, treats the deliverable as root cause + demonstrated behaviour change, not just a green test run: after the change reports the exact files changed, the underlying root cause, and an old-vs-new behavioural comparison (e.g. baseline query result vs. fixed query result against the real data), and syntax-checks each changed JS file with `node --check` alongside running the relevant tests. Confidence: 0.65
- Verifies task scope in Git before declaring done: runs `git status` and `git diff`, reviews every modified file, confirms only files belonging to the requested feature were touched, reverts any accidental unrelated changes, and leaves the user's own pre-existing uncommitted edits alone. The user makes this an explicit pre-finish requirement ("Run: git status, git diff — review every changed file; if unrelated files were changed → revert those changes"), paired with DO NOT commit / DO NOT push. Confidence: 0.85
- Before modifying code, verifies that referenced assets/files actually exist; if a required file is missing, reports it clearly rather than fabricating a substitute or altering the design to compensate. Confidence: 0.7
- After UI changes, expects verification across the entire affected page flow and across common mobile viewport sizes — no horizontal scrolling, no overflow/distortion, content readable, theme/state persisting across navigation — not just a single-page check; also expects build, lint, and console-error checks. Confidence: 0.75
- When the user says a just-fixed problem is still happening (e.g. bare "fix this" right after a fix was reported verified), treats the user's live UI as ground truth and re-runs the full flow end-to-end in the actual running app — API/curl-level checks alone can miss the remaining root cause (e.g. rate limiting caused by a polling hot-loop in other app clients). Confidence: 0.5
- ### RideEasy Workflow Quality Standard
  Treat a workflow task as complete only when the full continuous end-to-end flow works successfully, with no broken navigation, dead buttons, fake success states, disconnected screens, duplicate screens/navigation/state, or ride-state inconsistencies. Audit and test the entire User App as one connected chain: **Welcome → Authentication → OTP → Location → Home → Book Ride → Pickup → Drop → Find Trip → Route/Fare → Choose Ride → Search Driver → Driver Accepted → Driver Arriving → Driver Arrived → OTP → Start Ride → Live Ride → End Ride → Payment → Rating → Invoice → Home → Account/More**.

  Completion Requirements:
  1. Every screen must navigate to the correct next screen.
  2. Every button/action must perform its intended function.
  3. No fake success states or simulated production results.
  4. No disconnected or placeholder workflow steps.
  5. No duplicate screens, navigation stacks, API clients, socket connections, or state stores.
  6. Ride status must remain consistent across all screens.
  7. Frontend state must match the actual backend/database state.
  8. Never show a successful operation when the corresponding API/database operation failed.
  9. Pickup/drop addresses and coordinates must persist correctly through the booking flow.
  10. Route, distance, duration, fare, ride type, payment method, ride ID, driver information, and ride status must remain consistent throughout the ride lifecycle.
  11. Driver acceptance, arrival, OTP verification, ride start, live location, ride completion, payment, rating, and invoice must use the actual backend/API/Socket.IO flow where implemented.
  12. Completed rides must be correctly persisted and available in Ride History.
  13. Invoice must be derived from actual ride/payment data, never fabricated frontend values.
  14. Account, Profile, Ride History, Emergency Contact, Logout, Safety, and Help/FAQ flows must continue working.
  15. Existing theme, language, UI, and unrelated features must not be broken.

  Audit Before Completion:
  1. Audit the existing navigation.
  2. Audit all APIs used by the workflow.
  3. Audit Socket.IO connections and listeners.
  4. Audit ride-state management.
  5. Audit frontend/backend/database data flow.
  6. Test the complete workflow from application launch through invoice and return to Home.
  7. Test Account and More flows.
  8. Test API/database failure handling.
  9. Test relevant loading, error, retry, and empty states.
  10. Fix all discovered issues before declaring the workflow complete.

  Definition of Done: The RideEasy User App must work as one continuous, connected, real end-to-end workflow. A screen existing or an API returning successfully in isolation is NOT sufficient — the complete chain must be verified and the resulting data must persist correctly in the backend/database. Confidence: 0.85
- For end-to-end workflow audits against live servers, requires a strict per-step PASS/FAIL/BLOCKED report: for every workflow step include the screen/page, action tested, API endpoint/request used, Socket.IO event (if applicable), backend response/status, database persistence result, navigation result, and exact error on failure with the responsible file/component/API. A step must NOT be marked PASS just because the screen loads — the actual connected chain must be verified. Confidence: 0.85
- Sequencing preference for workflow audits: audit first strictly read-only (no code changes), deliver the full PASS/FAIL/BLOCKED baseline report, and only afterward propose/begin fixes; when something fails, report it as "FAIL → Root cause → File/component/API → Recommended fix" rather than fixing inline during the audit. Confidence: 0.85
- After the baseline audit, applies fixes in a strict priority order (critical end-to-end blockers → backend/API contract issues → socket/ride-state issues → navigation/state issues → UI/dead-button issues) using the smallest minimal changes. For each issue, first identify "Failure → Root cause → File/component/API → Minimal fix," then after implementing verify "Fix → Test → Result" and confirm it did not break previously-passing steps, then re-run the full end-to-end workflow before reporting completion. Confidence: 0.8
- Treats the repository as something that can change underneath an in-progress task: the user may commit the agent's working-tree changes and merge other branches mid-task (shifting line numbers, clearing `git status`); on detecting such a change the agent should confirm its edits and earlier fixes survived (via `git log`/`git show`/greps) and re-run the full verification (test suite + live check) against the current merged state before declaring done. Confidence: 0.5
- For "connect backend and user app" tasks, treats connectivity as needing the actual servers running end-to-end: confirms both running processes are the current project's instances (identified by PID + cwd/lsof, not config files) rather than a stale/trashed/duplicate copy holding the port, installs missing deps without touching backend source, then proves the chain with a CORS preflight from the frontend origin (checking Access-Control-Allow-Origin/Methods/Headers), a health/live check (reusing an existing endpoint, never creating/modifying one), a real unauthenticated and authenticated API round-trip that reaches the running backend (no mocks/fake success/static JSON — e.g. register returns real 201 with hashed user + JWT, profile returns real DB record), and a real Socket.IO client connection with a JWT — and reports PASS/FAIL for each. Confidence: 0.8
- When a UI defect is reported on one screen but the user says to check the whole group (e.g. "safety navigation is movable and help & support, check all pages in more option and fix it"), expects the same fix applied consistently to EVERY analogous page in that set — not just the reported screen — and each one verified afterward. Confidence: 0.6
- For Android/Capacitor (native mobile) work, expects verification on an actual physical device — build/install the debug APK, launch it, and inspect runtime logs — rather than relying only on the web or emulator build; also validates the real device→backend connectivity path (LAN IP over HTTP, cleartext/network-security policy, CORS for the Capacitor WebView origin). Explicitly requires that touch/gesture interaction feel smooth on the physical Android phone (e.g. "make the gesture smooth on the physical Android phone"). Confidence: 0.65
- When the user states a piece of configuration is already correct and explicitly says not to change it (e.g. the LAN IP / Wi-Fi / VITE_BASE_URL + VITE_SOCKET_URL setup — "DO NOT change the IP or Wi-Fi configuration blindly", "do not replace working LAN IP configuration with localhost"), treats that config as fixed: verifies the runtime actually uses it and hunts the true root cause elsewhere (e.g. the device's Wi-Fi being off) instead of churning working settings to chase the symptom. Confidence: 0.7
- Insists Socket.IO be verified independently of REST: a healthy HTTP endpoint does NOT mean WebSocket works, so real-time delivery must be confirmed by an actual client receiving the real event (testing both `websocket` and `polling` transports) — a claim that a driver/recipient got a request is only acceptable if that socket event's delivery was observed; otherwise it must be reported as unverified/blocked. Confidence: 0.75
- For real-time (Socket.IO) work, expects the COMPLETE multi-hop delivery chain verified end-to-end rather than merely "socket connected": the caller joins/presence-joins the correct room, the server's room actually contains the recipient's socket, the backend emits the exact event name the receiver listens for, and the payload contract matches — with per-hop temporary logs forming an expected log flow to compare against. Explicitly calls out the reconnect path: on reconnect the client re-authenticates and rejoins its driver room and refreshes its socket ID, and the backend must always target the CURRENT socket ID (a stale socket ID from a prior session can make the emit look successful while nothing arrives). Confidence: 0.7
- Treats restarting the long-lived local backend as part of finishing a code change: `node server.js` has no hot reload, so a process started before the edit still serves the old routes and answers a newly added endpoint with a JSON 404 (`{"message":"Not found"}`, surfaced in the app as a bare "Not found" alert). When the user reports such an error right after a change, confirm what is actually running on the port (PID/start-time/cwd) and restart the correct instance before assuming a code bug. Confidence: 0.6
- Measures real-time delivery by actual observed receipt, never by database presence flags: `socketId` / `isOnline: true` left over from an earlier session is not proof of a live socket — only room membership / an event actually received by a connected client counts as delivered. A dispatch must never silently swallow an offer either: it falls back to the connected-driver room whenever nothing was actually delivered (not only when the matched set is empty), and reports the true delivered count so on-screen diagnostics stay truthful. Confidence: 0.65
- The agent's shell exports `NODE_ENV=production` globally, which dotenv will not override, so launching the backend fails env validation; run the server and its scripts with `env -u NODE_ENV node …` so `Backend/.env` (development) applies. Confidence: 0.55
- Prefers proving a flow end-to-end over keeping the dev DB pristine: when the existing data genuinely cannot exercise the code path (all eligible drivers serve a different city / sit far outside the radius), accepts inserting one purpose-built test record into the live dev DB (chosen over "Don't touch data") — created through the real model so hashes/required fields/validators are satisfied, positioned so the funnel resolves (matched=1), re-verified against the DB immediately after, and reported with the new id, login, and the exact cleanup command/query to remove it. A live write like this is only justified when reported as correct behaviour with real data unavailable, never as a substitute for fixing a real filter/match bug. For multi-city testing this generalises to wanting a connectable test driver in EVERY service city: one login-ready, approved, subscription-active, in-area account per city (created through the real model, credentials reported, with a one-line removal command) so whichever city is being tested has a driver that can go Online — explicitly chosen over weakening city/vehicle/distance matching, which the user keeps fixed. Confidence: 0.6
- For real-time offer/notification delivery, wants an explicit end-to-end acknowledgement with distinct states kept truthful — matched / socket-available / event-sent / driver-received-and-acked — and never treats `io.to(room).emit()` as proof of delivery; the offer must stay durable/recoverable (same ride re-offered on reconnect, deduplicated by ride id on the client) rather than lost when the socket path fails. Also wants each delivery attempt persisted as a durable per-(ride, recipient) database record with truthful status/timestamps/failure reason (a dedicated dispatch-attempt collection, one row per matched recipient) so "matched" and "delivered" can never be conflated and delivery is auditable after the fact rather than only visible in transient logs. Confidence: 0.7
- When the task explicitly forbids fabricating data (e.g. a master prompt's "Do NOT create fake/test drivers" and "DO NOT manually insert fake ride_dispatches records"), runs the end-to-end verification on isolated throwaway infrastructure instead — its own MongoDB + backend on separate ports — driven by a real authenticated socket client and fixtures created through the real models, rather than inserting fake accounts/records into the real/dev database or faking delivered counts. Confidence: 0.6
