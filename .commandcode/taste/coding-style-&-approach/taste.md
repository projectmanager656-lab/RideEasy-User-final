# Coding style & approach
- Prefers surgical, minimal fixes over rewriting or rebuilding an app; when asked to remove a UI element (e.g. a nav tab), removes only that item and keeps the remaining items, layout, and styling exactly as they are. Explicitly forbids removing existing working functionality, deleting backend features to make the frontend compile, and replacing existing UI/branding/theming unnecessarily. Confidence: 0.95
- Prefers fixing routing, imports, and paths over creating anything new: never create a duplicate page/component/route if an equivalent already exists — wire the existing one up instead. Confidence: 0.9
- Prefers real backend integration over mock data whenever a real API exists; use existing API functions/contexts/models/controllers/routes rather than new parallel implementations. Confidence: 0.8
- Respects existing environment-based API config (e.g. VITE_* base URLs / apiBaseUrl helpers); do not hardcode backend URLs. Confidence: 0.8
- Dislikes hiding problems: no eslint-disable to silence errors, no deleting functionality to pass validation; fix the actual root cause and only touch files related to the issue. Confidence: 0.8
- When merging/repairing a project with contributions from multiple developers, keep the working functionality from all contributors rather than favoring one implementation. Confidence: 0.7
- Prefers reusing existing storage/session/onboarding state to gate a flow rather than inventing new flags; explicitly wants a search for an existing "step completed" mechanism before any new state is added. Confidence: 0.7
- When a visual/feature depends on existing global state (e.g. dark/light theme), wires it into the project's existing single source of truth — ThemeContext/provider, data-theme attribute, CSS-class theming, localStorage persistence — rather than creating a parallel theme system, duplicated state, or hardcoded per-page theme detection; the change must react instantly to the existing toggle with no refresh/reload. Confidence: 0.85
- Avoids adding new dependencies/packages; if something is missing, installs only what the existing project actually requires and never adds unnecessary packages. Before installing anything, checks package.json to see whether an existing dependency already covers the need, and never upgrades major dependencies or the framework (e.g. React Native/Expo) as part of a feature. Confidence: 0.85
- Cares about coherent, non-contradictory error/UX handling across a user flow: when the app directs the user to a next step (e.g. "account already exists — please log in instead"), that step must not then reject them with a generic contradictory error (e.g. "Invalid credentials"); duplicate-account detection and the login path it points to need to be consistent and lead somewhere that works. Confidence: 0.5
- When requesting theme or language work, expects app-wide completeness: "convert the remaining pages" / "apply to all pages" means EVERY page and shared component must support both dark and light themes and all app languages — no screen left hardcoded (bg-black/zinc/white literals) or with untranslated visible copy. Confidence: 0.85
- When connecting a frontend to an existing backend, treats the backend as a fully immutable, read-only contract: never edit backend files, routes, controllers, models, database/socket/auth logic, config, or dependencies; if the frontend calls an endpoint the backend doesn't expose, do NOT add/fake it in the backend — use another existing endpoint or leave it and report the missing API in the final summary. Confidence: 0.85
- Exception to the read-only-backend rule: when fixing a workflow (not just initial wiring up), the user explicitly lifts the read-only constraint for backend work ONLY on genuinely-missing/broken endpoints identified by the audit and required by the workflow — add real, DB-persisting handlers for just those endpoints (never mock/fabricated success), and never make unrelated backend changes. Confidence: 0.8
- For "connect the existing frontend to the existing backend" tasks, the scope is strictly frontend integration wiring only: no UI/UX redesign, no layout/color/animation/component/navigation changes, no refactoring unrelated code, no duplicate services/APIs, no dependency-tree or folder restructuring — only change the exact frontend code required to wire existing UI to the real backend APIs and socket contracts. Confidence: 0.85
- For cosmetic UI conversion requests, changes must be strictly limited to color/theme tokens and user-visible strings — explicitly "don't change other code": no logic, API, routing, layout, or feature changes may ride along with theming/localization edits. Confidence: 0.8
- When asked to "connect all .env files to use app db" / "connect user app to driver and admin app" (env/config wiring across the whole split-app stack), treats it as a config-only task: audit which files read env/MONGO_URI/base URLs, recognize that a frontend owns no DB connection (the backend owns the app DB) and thus wiring means pointing every app's env at the same backend that reads the DB, create only the missing dev `.env` file(s) for each app pointed at the shared backend, and leave application code, backend DB config, and other apps' env strictly untouched. Confidence: 0.8
- Follows the project's existing Socket.IO event naming and reuses existing socket events (rather than inventing new event names) for real-time ride updates; prevents duplicate event listeners when navigating between screens. Confidence: 0.7
- Routes all newly-added user-facing text through the project's existing translation/language mechanism instead of hardcoding new English-only strings, and adds each new key to EVERY supported app language dictionary at once (e.g. en/hi/mr in the same i18n extras file, checked for key collisions) rather than English-only. Confidence: 0.7
- Wants user actions to be discoverable via explicit, labeled controls on the relevant page, not hidden behind an implicit gesture: when the only way to change the profile photo was tapping an avatar, the user reported it as "can't show in change profile photo option in edit profile page" and asked for the option surfaced as buttons. Prefers purpose-specific, visible buttons (e.g. separate "Choose Photo" and "Take Photo") over a single opaque entry point, while sharing the underlying action logic between all entry points. Confidence: 0.6
- Expects every asynchronous action to have a proper loading state and to prevent duplicate button clicks while a request is in flight; never leaves the user on a permanently loading screen — shows a user-friendly error with retry/recovery where appropriate. Confidence: 0.7
- Preserves the existing project architecture and coding style: no duplicated functions/API clients/socket connections/state stores, no unused imports, dead code, or console spam, and no new dependencies unless genuinely required. Confidence: 0.7
- Prefers ONE reliable ride-state source of truth (e.g. a ride state store) with no screen maintaining conflicting ride statuses; maps backend status names cleanly into the frontend state rather than renaming backend statuses, and keeps booking data (pickup/drop coords, distance/duration/fare, ride type, payment method, rideId/driver info) consistent across navigation rather than relying only on temporary UI variables. Confidence: 0.7
- Wants success states driven by real backend/payment confirmation only — never auto-mark OTP as verified, ride as paid, or rating as submitted without backend confirmation; do not fake success, fake driver matching on frontend timers, or use mock coordinates/fares. Confidence: 0.7
- In this split-app monorepo (user-app, driver-app, admin-panel, Backend), scopes a fix to only the app/codebase containing the reported bug: an explicit "dont change other codebase" means do NOT touch sibling apps or the backend — fix only the affected app and, when the real fix would require another codebase (e.g. a missing chat backend endpoint/socket), report what's missing and offer to wire it rather than implementing it unprompted. Confidence: 0.75
- Treats secrets and API keys as strictly server-side: never places AI provider, backend, JWT, DB, or other credentials in frontend/mobile source, routes AI/LLM calls through the backend (which enforces the existing auth) instead of calling the provider from the client, reads keys from existing backend environment variables that already exist, does not overwrite existing .env values, and never commits secrets. Confidence: 0.75
- When adding AI/LLM-backed features, keeps the integration provider-agnostic and reuses an already-configured provider if present; prefers a clean, predictable backend response envelope consistent with the project's existing API format rather than introducing a conflicting one. Confidence: 0.65

Expects this applied across ALL pages, not just shared tokens: per-page decorative accent maps (icon tints, stat-card accents, one-off icon colours) must also be switched to the home-page brand colour so every page uses the "same colours". Confidence: 0.7
- A colour/brand change ("remove orange, in this project") is expected to be applied comprehensively across the whole app — the token definitions plus every hardcoded hex/rgba literal, boot splash, crash-screen button, offline page, and favicon — so no trace of the old colour survives anywhere. - For alignment/layout fixes, wants a structurally robust solution rather than pixel patching: a dedicated fixed-width indicator column plus a separate content column (each marker centred in its own slot/row), never fragile absolute positioning or magic numbers tied to a specific screen width, so the alignment holds across mobile sizes, when text wraps to two lines, and in both themes; the fix must not change the card's height, padding, or the text column's position. Confidence: 0.7
- Removing a UI element means removing its whole feature, not just its markup: delete the element, its click/touch handler, and every helper/state variable/i18n string that existed ONLY for it (grep-confirmed as otherwise unreferenced), with nothing left behind — no empty clickable area or invisible touch target — while touching only that component's own alignment/spacing if the removal throws off the surrounding layout. Confidence: 0.8
- When adding a shortcut that fills an existing form/state (e.g. tapping a recent search to populate the booking pickup/drop fields), expects state-aware logic instead of a blind overwrite: inspect the current state and fill the first empty slot (pickup, then drop), and when nothing is empty preserve the user's existing selection — or fall back to the app's existing selection behaviour — rather than silently replacing what they chose. Confidence: 0.65
- Treats a UI selection as a data transfer, not a label change: the full existing object (name, address, latitude, longitude, place ID) must be written into the real booking/state model so the map and fare stay consistent — never just the displayed text string, and never via a newly invented duplicate state variable or hardcoded value. Confidence: 0.65
- For a reported runtime error (e.g. an HTTP 404 shown on a specific screen), demands strict root-cause diagnosis before any edit: trace the exact failing request end-to-end (HTTP method, path, base URL, headers, body) against the actual backend route/registration and upstream dependency, state the concrete mismatch in the final explanation, and only then apply the minimal fix at the true source — never assume the cause, never randomly change/rename endpoints, and never suppress or hide the error. Confidence: 0.75
- Never exposes the database directly to the frontend: all data access must go through backend REST APIs (the frontend calls the existing API client), with MongoDB reachable only from the server. Confidence: 0.85
- For new backend API endpoints, expects the full production baseline — authentication, ownership/authorization checks, input validation, proper error handling, and pagination where applicable — reusing the project's existing auth/RBAC middleware rather than writing new auth or a parallel flow. Confidence: 0.75
- Extending an existing backend is strictly additive: do not create duplicate collections or duplicate APIs, and do not change, remove, or rename any existing endpoint (preserve the existing API contract); reuse existing code/models/indexes and match the already-defined schema exactly, using existing ObjectIds and relationships rather than inventing new collections or parallel implementations. Confidence: 0.75
- Treats the actual live database/schema (existing collections, fields, indexes, data) as the source of truth for integration work — audits what really exists before writing, so gaps are found against reality rather than assumed from the repo's file list. Confidence: 0.7
- Expects admin-managed records (e.g. coupons/offers created by the admin and stored in MongoDB) to be the single live source of truth: a record configured in the DB must appear in the app and apply correctly end-to-end, and behavior must be driven by that stored config/its explicit flags rather than inferred from display text/copy or hardcoded in code. Confidence: 0.6
- Wants a discount/reduction reflected explicitly in the fare UI, not just applied silently: the chosen ride shows the original fare struck through next to the reduced final amount (e.g. ₹602 → ₹502), with the coupon/deduction named, and the amount recomputes when the selected tier changes. Confidence: 0.6
- Expects ALL user-facing features/services to be genuinely persisted through the backend API into the real database, not kept browser-local: data written only to localStorage (e.g. a Safety page's emergency contacts or toggles) is treated as a bug "not showing in database" and must be wired to the existing DB-backed API rather than left local-only, and the user generalizes this beyond the one reported feature ("all service and features connect to backend api to db"). Confidence: 0.7
- Expects records derived from a completed lifecycle action to be persisted to the database as part of that action, not lazily on first screen/endpoint view: a completed ride with no row in `invoices` (because the invoice was only ever written by the invoice GET) counts as "not stored in the DB" and must be fixed by writing the snapshot at the completion step — idempotently, and wrapped so a persistence failure can never break the primary action — while leaving the existing lazy read path intact. Confidence: 0.7
- Maps API failures to accurate, status-specific user messages instead of one generic catch-all: a 401 should trigger session/auth handling, a 403 only the forbidden/blocked-account condition it actually represents (explicitly: never map every 403 to "Account suspended"), a 404 an endpoint/path-mismatch message, a 500 a backend-error message, and a network failure a connection message — never show a single misleading "endpoint not found" for every failure mode, and never surface a generic API failure as a specific account-status message. Confidence: 0.7
- When fixing a defect that causes a false positive (e.g. a user whose `blocked` field is `false` wrongly shown "Account suspended"), the fix must preserve and still enforce the genuine case: never weaken, bypass, disable, or remove the real protection to make the symptom disappear, never force the flag in the frontend, and explicitly verify both directions (false → allowed, true → correctly rejected). Confidence: 0.7
- Rigorous about boolean/status-flag semantics when diagnosing such bugs: an explicit stored `false` means not-blocked, `undefined`/missing follows the model's defined default, and only an explicit truthy value means blocked — never invert the check (`!field`), never trust stringly-typed values ("false"/"0"/"true"), and normalize server-side rather than coercing in the frontend. Confidence: 0.6
- Prefers targeted, scoped fixes over blanket/global ones: apply a fix mechanism only where it is actually required and keep compatibility intact, rather than wiring it globally across every page ("do NOT blindly run this [scroll handler] on every page") or rolling it out via mechanical find/replace ("do NOT blindly replace every 100vh"); e.g. mobile layouts should use dynamic viewport units (100dvh) where appropriate, not everywhere. Wants the interacting state to change while the default state stays pixel-identical. Confidence: 0.6
- Expects the current, non-deprecated API of the pinned library/framework version to be used (e.g. the appropriate Capacitor-6 keyboard resize mode), and the library's real behaviour verified against the installed version's semantics rather than assumed from memory. Confidence: 0.55
- For mobile keyboard handling, wants the surrounding chrome pinned and completely stationary: the top header/logo and bottom navigation bar must not move or resize when the Android keyboard opens — only the input/form area is allowed to scroll or adjust — and the keyboard must never scroll or shift the header. Rejects any fix where focusing an input causes the header to slide/clip; the default (keyboard-closed) layout must stay pixel-identical. Confidence: 0.7
- For authentication/session flow, expects a stored session to be honored across an app restart and an Android force-close: a returning user with a valid token is restored straight to the post-login home/Book page and must never be shown Login/Register again ("do not ask the existing user to log in again unnecessarily"). Only a genuinely invalid/expired session (401) clears the token and routes back to Login; transient failures (offline cold start, timeout, server hiccup) must keep the stored session and surface a retry/error state instead of being treated as "logged out". Wants this as distinct states — no-session vs. session-exists-but-profile-unloadable — rather than one fuzzy "not authenticated" bucket. Confidence: 0.8
- For Android/Capacitor system navigation, expects platform-conventional behavior rather than custom handling: the physical Back button follows the app's own navigation history and only exits the app when there is genuinely no previous page (it must not exit while a prior page exists), active ride/payment flows are protected from accidental exit, the hardware Home button backgrounds the app normally without resetting or logging the user out, and app resume restores the existing authenticated session and current app state where possible. Confidence: 0.75
- Wants app-lifecycle/event listeners (e.g. Capacitor back-button and resume listeners) registered exactly once for the app's lifetime with full cleanup on unmount — explicitly calls out preventing duplicate listeners and memory leaks. Confidence: 0.65
- Expects every page to be reachable from the app's navigation, not just by typing a URL: an orphaned route with zero inbound links (e.g. `/ride` having no entry point anywhere) is a bug to be fixed by adding it to the shared nav/More menu, and nav entry points should cover all pages consistently rather than leaving some destinations unreachable. Confidence: 0.6
- For mobile page layouts, wants fixed-chrome + dedicated-scroll-container architecture rather than whole-page scroll: the top header, summary/stat cards, tabs/search and the bottom navigation bar stay pinned (shrink-0) and must not move when the content scrolls, while ONLY the content list scrolls inside a single dedicated `flex-1 min-h-0 overflow-y-auto overscroll-contain` container inside a `flex h-full flex-col overflow-hidden` root. Explicitly asks for "a proper flex layout with a dedicated overflow-y-auto scroll container" and that the page/body never scroll (`scrollHeight == clientHeight`) and never scroll horizontally; the fixed bottom-navigation behaviour must be consistent across all pages. Restates this precisely when describing a reference behavior (map/pickup/drop and the bottom payment/action section all FIXED, only the middle ride/list scrolling), often scoping the treatment to the specific page named ("Apply this behavior only to the ride selection/Choose Ride page") while keeping all existing UI/colors/cards/spacing/icons unchanged. Confidence: 0.8
- Wants the dedicated scroll container hardened so scrolling is smooth and cannot leak: applies `overflow-x-hidden` + `touch-pan-y` to lock out sideways panning and `overscroll-contain` so the inner list's scroll never chains to the page behind it, plus momentum/scrollbar-hiding classes (`[-webkit-overflow-scrolling:touch]`, scrollbar-hidden) — expects this same class set reused so scrolling behaviour is consistent across pages. Confidence: 0.6
- Avoids gratuitous motion: explicitly says not to add unnecessary animation or delay — only the requested layout/behavior change, nothing extra that would make the app feel slower. Confidence: 0.5
- For mobile panel interactions, wants a genuine draggable bottom-sheet (collapsed → partially expanded → expanded snap points) with smooth, native-feeling touch/pointer gestures rather than a static panel: the sheet moves up/down over the map, and ONLY the panel moves — the map/top area, the ride summary, the bottom payment/action section and the bottom nav must stay stationary. The panel must never become a full-screen page. Wants the swipe to "feel natural like the reference video" and explicitly forbids artificial delays. Confidence: 0.6
- Revised the bottom-sheet drag model to be strictly handle-driven, and prefers explicit affordances plus strict gesture isolation over an implicit whole-panel gesture that steals in-list scrolling: an explicit drag handle/line at the top of the panel is the ONLY control that resizes it — the user must press-and-hold the handle, then drag up/down to expand/collapse — while the ride list keeps its normal scrolling exactly as-is, so a normal swipe/scroll anywhere in the list scrolls the list and must NEVER move the whole panel. The panel gesture must not activate on touches that begin on ride cards, buttons, or the list (use touch/pointer events), and on release the panel smoothly settles to the nearest snap position with no artificial delay. Confidence: 0.7
- When a non-editable sibling app (e.g. driver-app) depends on an existing backend socket/event contract, treats that contract as fixed and adapts only the editable side (Backend + the app being worked on) to match it — never redesigning/rewriting the sibling's flow or inventing parallel event names for the same purpose. Confidence: 0.6
- Never lets secrets reach logs when adding diagnostics. Development logging may capture API method/URL/status and socket connect/connect_error/disconnect/event names, but must never print passwords, JWT/session tokens, database passwords, or payment-gateway secrets (e.g. Razorpay secret). When testing auth directly (e.g. curl against the login endpoint), uses a throwaway test account and does not print credentials or tokens. Confidence: 0.8
- Wants temporary, clearly-marked development logging added specifically to diagnose connectivity/flow problems — with a consistent prefix convention such as `[API] <method> <URL>`, `[API] <status>`, `[SOCKET] connect / connect_error / disconnect`, `[socket] event name / ride id` — and removed (or the debug flag unset) once the flow is confirmed working, rather than leaving noisy logging in production. Confidence: 0.7
- Prevents duplicate side effects on retries: repeated button presses or a socket-delivery failure must never create a duplicate ride — reuse the existing pending-ride/retry mechanism and keep the user waiting rather than inserting another record. Confidence: 0.65
- For uploaded files/images, prefers filesystem (disk) storage with only the resulting URL saved as a String field in the database — explicitly rejects Base64 image storage, storing image binaries in MongoDB, and third-party image hosts (e.g. Cloudinary). Wants a server-generated unique filename (never trusting the client's original filename), an enforced max file size, and an image MIME allow-list (jpeg/png/webp) via multer disk storage; also lets the browser/axios set the multipart boundary rather than manually setting `Content-Type: multipart/form-data`. Confidence: 0.6
- When asked to add a field to an existing profile/account page ("add gender and date of birth ... also edit option"), expects it wired end-to-end — backend model field + validation, a display row, and an editable control integrated into the page's EXISTING inline Edit form (extending the current save/cancel toggle rather than adding a separate edit UI) — not merely rendered read-only. Confidence: 0.6
- Prefers date-only values (e.g. a date of birth) stored as a `YYYY-MM-DD` string instead of a `Date`, so the value can't shift a day across timezones, and rendered through the app's existing localized month names rather than a hardcoded English format. Confidence: 0.55
- In the split-app stack (Backend + user-app + driver-app + admin-panel), expects the passenger and driver apps to be built against the SAME backend: a ride created against one server is only dispatched on that server, so a backend mismatch (e.g. one app still pointed at a stale deploy while the other uses the LAN backend) makes cross-app flows silently fail with no code bug in the dispatch path. Confidence: 0.6
