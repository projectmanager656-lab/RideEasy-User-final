# Coding style & approach
- Prefers surgical, minimal fixes over rewriting or rebuilding an app; when asked to remove a UI element (e.g. a nav tab), removes only that item and keeps the remaining items, layout, and styling exactly as they are. Explicitly forbids removing existing working functionality, deleting backend features to make the frontend compile, and replacing existing UI/branding/theming unnecessarily. Confidence: 0.95
- Prefers fixing routing, imports, and paths over creating anything new: never create a duplicate page/component/route if an equivalent already exists — wire the existing one up instead. Confidence: 0.9
- Prefers real backend integration over mock data whenever a real API exists; use existing API functions/contexts/models/controllers/routes rather than new parallel implementations. Confidence: 0.8
- Respects existing environment-based API config (e.g. VITE_* base URLs / apiBaseUrl helpers); do not hardcode backend URLs. Confidence: 0.8
- Dislikes hiding problems: no eslint-disable to silence errors, no deleting functionality to pass validation; fix the actual root cause and only touch files related to the issue. Confidence: 0.8
- When merging/repairing a project with contributions from multiple developers, keep the working functionality from all contributors rather than favoring one implementation. Confidence: 0.7
- Prefers reusing existing storage/session/onboarding state to gate a flow rather than inventing new flags; explicitly wants a search for an existing "step completed" mechanism before any new state is added. Confidence: 0.7
- When a visual/feature depends on existing global state (e.g. dark/light theme), wires it into the project's existing single source of truth — ThemeContext/provider, data-theme attribute, CSS-class theming, localStorage persistence — rather than creating a parallel theme system, duplicated state, or hardcoded per-page theme detection; the change must react instantly to the existing toggle with no refresh/reload. Confidence: 0.85
- Avoids adding new dependencies/packages; if something is missing, installs only what the existing project actually requires and never adds unnecessary packages. Confidence: 0.85
- Cares about coherent, non-contradictory error/UX handling across a user flow: when the app directs the user to a next step (e.g. "account already exists — please log in instead"), that step must not then reject them with a generic contradictory error (e.g. "Invalid credentials"); duplicate-account detection and the login path it points to need to be consistent and lead somewhere that works. Confidence: 0.5
- When requesting theme or language work, expects app-wide completeness: "convert the remaining pages" / "apply to all pages" means EVERY page and shared component must support both dark and light themes and all app languages — no screen left hardcoded (bg-black/zinc/white literals) or with untranslated visible copy. Confidence: 0.85
- For cosmetic UI conversion requests, changes must be strictly limited to color/theme tokens and user-visible strings — explicitly "don't change other code": no logic, API, routing, layout, or feature changes may ride along with theming/localization edits. Confidence: 0.8
