# Taste
- Prefers surgical, functionality-preserving fixes: never blindly accept one side of a merge conflict ("Accept Current"/"Accept Incoming"), never revert a file or replace it with an older copy, and merge both sides intelligently to preserve all existing functionality. Confidence: 0.6
- Prefers strictly scoped changes: do not modify unrelated files or make unrelated changes, and remove duplicates only when they are genuinely duplicated. Explicitly fences off sibling apps and legacy folders (e.g. "do not modify driver-app/, Backend-Old/", "inspect Backend only if needed, do NOT modify") and will not touch features outside the request (scheduling, notifications, fares, payments, OTP, sockets, lifecycle, API). Repeats "Keep EVERYTHING else exactly as it is" and enumerates an explicit do-not-touch list per task. Confidence: 0.8
- Prefers the smallest safe change: explicitly rejects large refactors and consolidation beyond what the fix requires. Confidence: 0.7
- Wants the exact root cause of a bug identified and reported before modifying anything — trace the existing implementation and routing first, "do not guess"/"do NOT assume the cause", often enumerating candidate causes and requiring the real one be found rather than guessed. Confidence: 0.7
- Wants errors root-caused separately and reported honestly rather than hidden, even when an initial fix surfaces a new error. Confidence: 0.6
- Expects hard safety boundaries: no destructive database operations, no deleting data, and no modifying `.env` secrets. Confidence: 0.7
- Expects focused verification of only the changed flows, plus explicit test results and confirmation that previously fixed behavior was not regressed. Confidence: 0.6
- Expects UI/visual changes to be checked in both light and dark themes. Confidence: 0.55
- Wants assets kept local to the project: reuse existing project assets when present, do not hotlink external image URLs, do not use emojis, and do not hand-draw approximations of official brand logos. Third-party/brand marks must stay the real full-color official artwork — no monochrome/grayscale versions, no recoloring every logo with one CSS color, and no faking color onto a monochrome asset. Confidence: 0.7
- Prefers final reports kept short and ordered — typically a numbered list covering the root cause, what was changed, exact files modified, test/build results, and any remaining limitations. Confidence: 0.7
- Prefers lightweight verification proportionate to the change: a frontend build (and lint/targeted check) is expected, but explicitly avoid large E2E/browser harnesses unless absolutely necessary. Confidence: 0.6
- Wants disabled UI states kept clearly recognizable WITHOUT altering the content: never fade, blur or desaturate a logo/brand mark — grayscale payment logos were explicitly rejected ("I DO NOT want grayscale payment logos"). Signal disabled state through the button's own surface/border/cursor/text (muted label, `cursor-not-allowed`) so the mark is untouched, while the underlying disabled logic stays unchanged. Confidence: 0.8
- Prefers cross-browser CSS solutions where appropriate (e.g. covering Chromium/WebKit and Firefox) rather than a single-engine approach. Confidence: 0.5
